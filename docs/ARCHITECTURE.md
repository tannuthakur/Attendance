# Architecture & conventions

`SPEC.md` is the source of truth for **what** to build. This file explains **how** the code is
organised so every module looks the same.

## Layout

```
src/app/(auth)/…            public auth pages
src/app/(app)/…             authenticated pages (layout requires an active profile)
src/app/(app)/<module>/export/route.ts   CSV export of the current filtered list
src/features/<module>/
  schemas.ts        zod schemas (shared by forms + actions). Pure, unit-tested.
  list-config.ts    ListConfig for the module's listing (sortable columns, filters). Pure.
  queries.ts        'server-only' reads (take ListParams, return { rows, total }).
  actions.ts        'use server' mutations, all built with adminAction().
  components/       client + server components for the module.
src/lib/billing/    PURE billing engine (no I/O, 100 % coverage). Never import Supabase/Next here.
src/lib/…           shared helpers (list-params, dates, format, csv, invoice-number, …)
src/components/ui   shadcn/ui primitives
src/components/data-table   generic server-driven DataTable
supabase/migrations          schema, RLS, RPCs, list views
```

## Database

- All business tables have RLS: SELECT for active users, writes for admins (`is_admin()`).
- Multi-row / transactional writes are Postgres functions called with `supabase.rpc(...)`:
  `set_employment_status`, `change_project_status`, `assign_employees`, `upsert_attendance_bulk`,
  `save_holidays`, `delete_employee`, `next_invoice_number`, `save_invoice`, `invoice_action`,
  `log_invoice_download`, `refresh_employee_statuses`, `touch_last_login`.
- Functions raise exceptions whose **message is a code** (e.g. `INVALID_TRANSITION`). `src/lib/db-errors.ts`
  maps codes and SQLSTATEs (23505 duplicate, 23P01 overlap, 23503 in use, 23514 check) to friendly messages.
- Read models for lists are views (security_invoker): `employee_list`, `project_list`, `invoice_list`
  (excludes soft-deleted), `attendance_list`, `holiday_list`, `assignment_list`, `assignment_current_rates`,
  `user_directory` (id + full_name of active users, readable by viewers).
- `activity_log` is written by triggers on every main table. `parent_id` = employee/project/invoice id of the row.
- `src/types/database.ts` is generated by `node scripts/gen-db-types.mjs` (edit the schema description there)
  or by `pnpm db:types` when Supabase is running.
- "Today" = `business_today()` in SQL, `getToday()` (features/lookups/queries) in TS.

## Server actions

```ts
'use server';
export const createThing = adminAction(thingSchema, async (input, { supabase, user }) => {
  const row = check(await supabase.from('things').insert(...).select().single(), { DUPLICATE: 'Name already used' });
  return { id: row.id };
}, { revalidate: ['/things'] });
```

- `adminAction` = requireAdmin → zod safeParse → body → revalidatePath → `ActionResult<T>`
  (`{ ok: true, data } | { ok: false, error: { code, message, fieldErrors? } }`). Raw DB errors never leak.
- Use `check(res, overrides)` to throw on Supabase errors; `throw new ActionFailure(code, message)` for business rules.
- Viewers calling any action get `{ ok: false, error: { code: 'FORBIDDEN' } }`.
- Client: call the action, then `toast.success(...)` / `toast.error(res.error.message)`; set
  `fieldErrors` on the form with `form.setError`.

## Listing pages

1. `list-config.ts` exports a `ListConfig` (`satisfies ListConfig`).
2. Page (server): `const params = parseListParams(await searchParams, config)`; `const { rows, total } = await listX(params)`.
3. Query applies `q` (ilike over several columns via `.or()`; escape with `escapeSearch`), filters,
   `.order(sortColumn)`, `.range(from, to)` with `{ count: 'exact' }`. Sort ids map to DB columns in the query.
4. Client table component renders `<DataTable>` with columns (`meta: { label }` makes a column sortable/toggleable
   when its id is in `config.sortable`), `filters: FilterField[]`, `exportHref="/<module>/export"`, `actions`.
5. `export/route.ts` re-parses the same params, loads up to `EXPORT_LIMIT` rows and returns `csvResponse()`.

## Auth in UI

- `useIsAdmin()` / `<AdminOnly>` hide create/edit/delete/status controls for viewers.
- Admin-only pages (edit/new) call `await requireAdminPage()` → 403 page for viewers.
- `getCurrentUser()` (server, cached per request).

## Formatting

- Dates `formatDate()` → `08 Oct 2026`; money `formatMoney(amount, currency)` → `USD 2,750.00`.
- Money math only with `decimal.js` (`Dec`/`money()` from `@/lib/billing`). DB numerics arrive as JS numbers;
  convert with `money(value)` before arithmetic.
- Badges: `components/status-badge.tsx` (attendance colours come from `attendance_statuses.color`).

## Cross-module contracts

Detail pages use `?tab=<name>` so tabs are server-rendered. Some tabs are owned by another module and exported
as async Server Components that load their own data:

| Component | File | Owner | Rendered in |
|---|---|---|---|
| `EmployeeAttendanceTab({ employeeId, searchParams })` | features/attendance/components/employee-attendance-tab.tsx | attendance | /employees/[id]?tab=attendance |
| `ProjectAttendanceTab({ projectId, searchParams })` | features/attendance/components/project-attendance-tab.tsx | attendance | /projects/[id]?tab=attendance |
| `ProjectBillingCyclesTab({ projectId })` | features/invoices/components/project-billing-cycles-tab.tsx | invoices | /projects/[id]?tab=cycles |
| `ProjectInvoicesTab({ projectId })` | features/invoices/components/project-invoices-tab.tsx | invoices | /projects/[id]?tab=invoices |
| `EmployeeInvoicesTab({ employeeId })` | features/invoices/components/employee-invoices-tab.tsx | invoices | /employees/[id]?tab=invoices |

Billing input for a project + period is loaded by `loadBillingSource()` (features/invoices/billing-source.ts);
outdated detection is `refreshOutdatedFlags()` (features/invoices/outdated.ts).

## Tests

- `tests/unit/**` – pure logic (Vitest, jsdom). `tests/component/**` – Testing Library; use
  `tests/component/test-utils.tsx` (`renderWithUser`, `nav` router mock, `ADMIN`/`VIEWER`).
  Mock server actions with `vi.mock('@/features/x/actions', …)`.
- `tests/integration/**` – real local Supabase. `actAs('admin' | 'viewer')` signs in a test user and makes
  server actions use that session (see `tests/integration/setup.ts`). Call actions directly.
- `supabase/tests/*.test.sql` – pgTAP (RLS, constraints, functions).
- `tests/e2e/**` – Playwright against the seeded database (`login(page, 'admin')`).
